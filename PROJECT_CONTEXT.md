This file exists so any Claude Code session starting fresh in this repo has full context without the user needing to re-explain. Read this first.

## What this project is

**Personal Time Capsule** — an open-source, non-commercial, public-good standard and toolkit that lets ordinary people preserve their digital lives (email, photos, writing, audio, video) as historically useful, privacy-respecting, legally governed archives for future generations. Not a company, not monetized.

Full framing lives in `README.md`, `VISION.md`, and `PRINCIPLES.md` at repo root — read those before doing design work.

## Key design decisions already locked in

- Build on **BagIt** (packaging), **PREMIS** (preservation metadata), **OAIS/ISO 14721** (reference model), **LOCKSS** philosophy, **SHA-256** (integrity), **XChaCha20-Poly1305** (payload encryption), and **SLIP-0039** (key splitting) — do not reinvent these. See `STANDARDS.md` for why each one and what it's used for.
- A capsule **is a BagIt bag**. `capsule.yaml` is a root-level BagIt *tag file* (checksummed via `tagmanifest-sha256.txt`), not payload — see `FORMAT.md`.
- The **human-context layer is payload**, not metadata-about-metadata: `data/person/` (biography, timeline, people, places) lives under `data/` and is checksummed in `manifest-sha256.txt` alongside photos/email/etc., per Principle #6.
- Privacy zone and release policy are declared **capsule-wide by default, with optional per-named-collection overrides** in `capsule.yaml`, and optional per-item overrides in a separate, sparse `privacy-overrides.yaml` (a tag file, frozen at sealing like `capsule.yaml`) for the rare item that needs to differ from its own collection. `capsule.yaml` stays a bounded, readable file — see `PRIVACY.md`.
- **Encryption: XChaCha20-Poly1305 payload encryption, SLIP-0039 key splitting, one key per collection (not per capsule).** Chosen over AES-256-GCM for nonce-misuse safety (Rust has no stdlib crypto either way, so that wasn't the deciding factor) and over raw Shamir's Secret Sharing for SLIP-0039's self-checking, human-transcribable share format. A collection with its own `release_policy` needs its own `encryption` override too, or unlocking it would also unlock everything else sharing its key. Item-level (`privacy-overrides.yaml`) isolation is a known, unsolved gap — see `ENCRYPTION.md`.
- **Preservation and access are separate** — an institution can hold/verify/replicate a capsule while being cryptographically unable to read it before a release condition is met.
- Release policy is **configurable per collection** (e.g., photos vs. email vs. private journal can each have different lock periods), not one global unlock date.
- No promise of "cryptographically impossible to open" — layered protection (crypto + legal + custodial), documented assumptions, no dependency on any single external service surviving decades.
- **Preserve the mess** — raw/unedited material is welcome; curation is additive, never required.
- **Metadata is event/batch-granularity, not per-file.** `data/provenance/events.yaml` (payload, like `data/person/`) logs the capsule's *pre-seal* history — origination, imports, annotation, screening, sealing — with free-text provenance on import events. Deliberately no PREMIS Object record per payload file; that's redundant with the BagIt manifest and works against Principle #6. See `METADATA.md`.
- **Post-seal history lives in a second, deliberately unsealed file.** `preservation-log.yaml` (bag root, NOT in `manifest-sha256.txt` or `tagmanifest-sha256.txt`) logs everything that happens after sealing — encryption, deposit, fixity checks, succession transfers, release/unlock/access — because appending to a checksummed file after the checksum was committed to would break what "sealed" means. Recommended fixity-check cadence: at least annually, plus after any custody transfer. See `INTEGRITY.md`. (Note: `events.yaml`'s schema originally, incorrectly, allowed all these post-seal types too — fixed while writing `ENCRYPTION.md`; `events.yaml` is pre-seal-only, stages 1-5.)
- Privacy tooling (sensitive-data scanning, redaction, privacy zones: public/restricted/never-release) is core, not an add-on. `PRIVACY.md` recommends an open (not enforced) starter vocabulary for scan categories — financial, credentials, medical, government-id, third-party-privacy, other.
- **`after_death`/`after_death_plus_years` triggers are confirmed by the trustee quorum, not one executor alone.** The executor/estate representative (`ACTORS.md`) confirms death and notifies trustees, but each trustee is expected to independently satisfy themselves before contributing their share — reuses `ENCRYPTION.md`'s existing quorum rather than a separate confirmation mechanism. Recommended (not mandated) evidence standard: a named confirming party plus at least one independent corroborating source, logged in a `release_trigger` `preservation-log.yaml` entry. `immediate`/`fixed_date` need no real confirmation; `never` has nothing to confirm, ever. See `ACCESS.md`.
- **`capsule.yaml`'s `custody` section is a frozen snapshot of the original plan, not a live pointer** — same convention as `status.lifecycle_stage`/`events.yaml`. The real current custodian is tracked via `succession_transfer` entries in `preservation-log.yaml`. Custodian succession triggers on explicit notice OR a documented unresponsiveness timeout (number TBD by Phase 3's custodian agreement). Trustee succession (re-splitting the key with an adjusted roster) can only happen reactively, while a live quorum still exists — once quorum is lost there's no recovery path, a property of Shamir's Secret Sharing, not a spec gap. A no-fault trustee departure re-splits the same key; a for-cause removal requires rotating the key itself (re-encrypting, a `reseal`-class operation) since the old key would otherwise still be reconstructible from an unrevoked old share. See `CUSTODY.md`.
- **Deed of gift: creator retains copyright; custodian gets custody + a license.** Matches Principle #2 — a family's literary/copyright rights in the actual content don't pass to the institution, just the physical/digital custody and a license broad enough to preserve/replicate/provide access per the recorded release policy. `legal/`'s contents (inside a capsule bag) are checksummed in `tagmanifest-sha256.txt` and frozen at sealing, same as `capsule.yaml` — a signed legal instrument should be tamper-evident from execution, and there's no post-seal-mutation problem to solve here (unlike `preservation-log.yaml`) since it's normally executed alongside the `custody` decision, before or at sealing. See `DEED_OF_GIFT.md`. **Phase 3 documents carry a stronger caveat than Phase 2's** — "not usable" pending real attorney review, not just "open to challenge."
- **Access restriction agreement merges "Access Restriction" and "Posthumous Release"** (kept separate in the founding conversation) into one document, since `ACCESS.md` already unified those triggers under one `release_policy` vocabulary. Its release schedule is per-collection, matching how release policy/encryption already vary per collection. Breach (early release, or refusing to release once triggered) is now a third `CUSTODY.md` succession trigger — chosen over inventing a new, potentially decades-long-lived enforcement role, since it's self-enforcing and doesn't require anyone still being around to sue. See `ACCESS_RESTRICTION_AGREEMENT.md` and `CUSTODY.md`'s amended "What triggers it" section.

## Working style / workflow preferences

- Changes go through a **feature branch + PR**, not direct pushes to `main`. This has been the actual pattern used (PRs #1–12 so far) — keep doing it.
- The user is non-technical-by-trade but hands-on; explain tradeoffs plainly, don't assume deep git/crypto background.
- The project is explicitly meant to be developed **in public** — docs should read as if archivists/historians/lawyers may be watching and are invited to disagree.
- Keep tone of docs matter-of-fact and a little idealistic, not corporate/marketing.
- When a design decision has real tradeoffs and isn't purely technical, ask the user rather than picking silently — this has worked well for licensing and the `capsule.yaml` structural decisions.
- Avoid duplicating living status/tracking information across multiple docs (e.g. phase progress) — point to the one canonical doc (`ROADMAP.md`) instead, to prevent drift. This file was itself a repeat offender until this rewrite.
